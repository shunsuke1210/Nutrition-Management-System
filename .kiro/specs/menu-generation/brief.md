# Brief: menu-generation

## Problem
必要な栄養素・カロリーが分かっても、それを満たす具体的な献立を毎日自分で考えるのは大きな負担であり、特にダイエット中は空腹感やマンネリ化で挫折しやすい。また、生成された献立の栄養価が不正確だと、ユーザーの信頼を損なう。

## Current State
プロジェクトは新規であり、献立生成の仕組みは存在しない。nutrition-engine が算出する栄養目標値、user-profile が保持する嗜好・NG食材等を入力として利用する前提。

## Desired Outcome
nutrition-engineの栄養目標値・PFC比率・食事制限設定とuser-profileの嗜好・NG食材を踏まえた1週間分（朝昼晩+間食）の献立が自動生成され、栄養価がDBで検証済みの信頼できる数値として提示される状態。ユーザーは1日単位・1週間単位のどちらでも献立を再生成・差し替えでき、献立への満足度（好き/苦手）をフィードバックすると次回以降の生成に反映される状態。また、個々の食事（朝食/昼食/夕食/間食）を選択すると、そのレシピ詳細と「もう一品追加するなら」の補助的な提案がその場で生成される状態。

## Approach
Claude API（Messages API）を用いて、構造化出力（`strict: true` のtool use / JSON Schema制約）で献立を生成する。食材はClaudeに自由記述させず、事前に用意した食品ID一覧（MEXT日本食品標準成分表 八訂ベース）からのtool呼び出しで選択させることで、DB照合を決定論的に行う。生成後、選択された食品IDと分量（正規化された単位）を食品成分DBと突き合わせて実際の栄養価を計算し、nutrition-engineの目標値との差分を検証する。ユーザーからの満足度フィードバック（好き/苦手）は次回のプロンプトに反映し、苦手な食材・料理の再提案を避ける。食事制限設定（タイプ・強度・その他自由記述）はプロンプトのcontextとして渡し、その制約に沿う献立のみを生成する。

献立の差し替えは1日単位と1週間単位の両方をサポートする。1日単位のみで差し替えると、その日の栄養目標にだけ最適化されるため、残り6日と食材が重複したり、週全体の栄養バランス調整が崩れたりする偏りが生じうる。これを避けるため、1日単位の差し替えでも既に確定している他6日分の献立（食材・料理名）をプロンプトのcontextとして渡し、重複を避けるよう指示する。それでも偏りが気になる場合や大きく方向性を変えたい場合のために、1週間分をまとめて再生成する差し替えも提供する。

各食事セルの詳細表示要求に対しては、オンデマンドでレシピ詳細（材料・分量・手順・栄養内訳）を生成し、あわせて「もう一品追加するなら」の補助的な副菜候補を1〜2件提案する。

## Scope
- **In**:
  - 1週間分の献立生成（朝昼晩+間食、Claude APIの構造化出力）
  - 食事制限設定（タイプ・強度・その他自由記述）を反映した献立生成
  - 食材選択を食品ID一覧に制約するtool定義と実装
  - 食品成分DB（MEXT八訂）とのマッピング・栄養価計算・検証
  - 分量単位（g / 個 / 大さじ 等）の正規化テーブル
  - 1日単位（他6日を考慮した重複回避付き）・1週間単位の両方の献立再生成・差し替え
  - 個別の食事（朝食/昼食/夕食/間食）のオンデマンドなレシピ詳細生成、および追加副菜の提案
  - 献立への満足度フィードバック（好き/苦手）の収集と次回生成プロンプトへの反映
  - 計画献立に基づく1日あたりの摂取カロリー（計画値）の算出・提供（user-profileの日次ログがデフォルト値として利用する）
- **Out**:
  - 栄養目標値そのものの計算（nutrition-engine の責務）
  - プロフィール・嗜好情報・食事制限設定・摂取カロリー実績の保存（user-profile の責務）
  - 献立・レシピ・買い物リストの画面表示（results-dashboard の責務）

## Boundary Candidates
- Claude APIとの連携・プロンプト設計・構造化出力の制御
- 食品成分DBとの照合・栄養価検証ロジック
- 満足度フィードバックの学習・反映

## Out of Boundary
- 栄養目標値の算出ロジックは持たない（nutrition-engineから受け取る）
- 結果画面のUI・買い物リスト表示は行わない（データは提供するがレイアウトはresults-dashboardが担う）

## Upstream / Downstream
- **Upstream**: user-profile（嗜好・NG食材・調理時間/スキル/予算感・食事制限設定等）、nutrition-engine（栄養目標値・PFC比率）
- **Downstream**: results-dashboard（生成された献立・レシピ詳細・栄養価検証結果・買い物リストの元データを表示）、user-profile（計画献立kcalを摂取カロリー実績のデフォルト値として提供）

## Existing Spec Touchpoints
- **Extends**: なし（新規spec）
- **Adjacent**: user-profile・nutrition-engine（入力元）、results-dashboard（出力先）

## Constraints
- LLMはClaude API（Anthropic Messages API）を使用する
- 食品成分DBはMEXT「日本食品標準成分表（八訂）増補2023」を一次データソースとし、出典表示（"日本食品標準成分表（八訂）増補2023年から引用"）を行う。私的出版社の独自デジタル版（医歯薬出版等）は使用しない
- 食材選択はClaudeの自由記述ではなく、既知の食品IDリストからのtool呼び出しで行う
- 技術スタックは design フェーズで決定
