## Implementation Notes
- (1.1) Unlike `user-profile`/`nutrition-engine`, this spec's tasks.md has NO `_Boundary:_`/`_Depends:_` annotations on tasks 1.1-1.5 and 2.1-2.2 (the "Foundation" groups — shared infrastructure with no single named design.md component to map to). Annotations DO exist starting from task 3.1 onward (component-mapped tasks). For the annotation-less Foundation tasks, the parent controller determines scope itself from the task's literal file-creation instructions and existing repo conventions — this is expected and not a spec defect; future Foundation-group tasks (1.2-1.5, 2.1-2.2) will need the same treatment. Created `005_create_food_items.sql`/`006_create_unit_conversions.sql` matching design.md's Physical Data Model exactly (independently byte-for-byte verified by review, including the `source_citation` DEFAULT citation string). Extended the EXISTING shared `server/src/db/migrate.test.ts` (its `EXPECTED_TABLES` array plus a few focused new constraint tests) rather than creating a new per-migration test file — this repo's established convention (from `user-profile`) is ONE shared migration test file covering all tables, not one file per migration; `migrate.ts` itself needs zero code changes since it's a generic, auto-discovering runner. **Genuine non-obvious SQL semantic surfaced and caught by review**: `unit_conversions`' `UNIQUE(food_id, unit_code)` constraint provides ZERO deduplication protection for generic (`food_id IS NULL`) entries — standard SQL never treats two NULLs as equal, even within a composite UNIQUE constraint, so two NULL-food_id rows can share the same `unit_code` without violating the constraint. This is correct, intended behavior per design.md's literal schema (not a bug), but the round-1 test claiming to prove this only tested a trivial contrasting case (different `unit_code`s, which trivially wouldn't collide regardless of NULL semantics) — round-1 review independently reproduced the actual behavior via a standalone script and required a genuine same-`unit_code` test; round-2 review independently reproduced it AGAIN before approving. **Lesson**: when a test's name/claim involves a NULL-related uniqueness or equality semantic, verify the test actually constructs the case where NULL-vs-NULL comparison would matter (same values on every OTHER composite-key column) — a "different values elsewhere" variant proves nothing about NULL handling specifically, no matter how the test is named. This exact behavior is directly relevant to task 2.2 (seeding generic/NULL-food_id unit entries) and task 3.2 (`UnitConversionService` querying generic entries by `unit_code`) — future seed data for generic units must avoid accidentally inserting duplicate `unit_code` rows itself, since the DB will not catch it.
- (1.2) `007_create_menu_plan_tables.sql` bundles all 4 tables (`week_menu_plans`/`day_menus`/`meal_slots`/`meal_ingredients`) into ONE file, per the task text's own file-naming instruction (unlike task 1.1, which split into 2 files) — matches design.md's Physical Data Model exactly, independently re-verified column-by-column by review. `day_menus` deliberately has TWO separate UNIQUE constraints (`(week_start_date, day_index)` composite AND a standalone `day_date UNIQUE`) — both genuinely independently enforced and tested (a row colliding on one but not the other still fails), since `day_date` is the natural calendar-date identity while `(week_start_date, day_index)` is the aggregate-position identity; both must hold for the `WeekMenuPlan`→`DayMenu[7]` aggregate invariant to be sound. **Deliberate, scrutinized design choice**: `meal_ingredients.food_id REFERENCES food_items(food_id)` has NO `ON DELETE CASCADE` (every other FK in this migration does) — confirmed by review as intentional, not a spec gap, based on 3 independent signals: (a) design.md applies the identical no-cascade pattern to the structurally analogous `supplementary_ingredients.food_id` (a later table, task 1.3), consistently across two separate tables — inconsistent if it were a copy-paste mistake; (b) contrast with `unit_conversions.food_id` (task 1.1), which DOES cascade — `unit_conversions` is pure secondary lookup data meaningless without its parent food, whereas `meal_ingredients` rows are historical generated-menu records with independent lifecycle meaning; (c) design.md's own Revalidation Triggers section anticipates `food_items` being revised when the MEXT data source version updates — silently cascade-deleting historical meal records on a reference-data refresh would be a genuine data-loss bug. **Lesson**: when one FK in a migration deviates from an otherwise-consistent CASCADE pattern, don't assume it's an oversight — check whether design.md applies the SAME deviation elsewhere for a structurally similar relationship (a strong signal of intent) before deciding whether to escalate or just implement as literally specified; here, cross-referencing a table 2 tasks away (`supplementary_ingredients`, not yet built) was the key evidence. The 3-level CASCADE chain (`week_menu_plans`→`day_menus`→`meal_slots`→`meal_ingredients`) and the non-cascading `food_items` FK were both tested with a fully realistic, FK-satisfying fixture chain (a real `food_items` row inserted first) and verified via row-count assertions at each level, plus a mutation test (temporarily adding the CASCADE clause) confirming the non-cascade test is genuinely load-bearing.
- (1.3) `008_create_recipe_detail_tables.sql` (recipe_details/supplementary_suggestions/supplementary_ingredients) and `009_create_satisfaction_feedback.sql` (satisfaction_feedback) match design.md's Physical Data Model exactly (independently re-verified column-by-column by review). `supplementary_suggestions`' 4 delta columns (`energy_kcal_delta`/`protein_g_delta`/`fat_g_delta`/`carb_g_delta`) deliberately have NO `>=0` CHECK, unlike almost every other numeric column in this schema — they represent signed deltas (a supplementary dish's nutrition impact relative to nothing, can legitimately be negative or positive), confirmed correct against design.md's own unconstrained spec for these columns. `supplementary_ingredients.food_id` reapplies task 1.2's already-confirmed non-cascading FK pattern (historical record → reference data, restrict not cascade) — now established as consistent across BOTH ingredient-junction tables in the schema. **`satisfaction_feedback` deliberately has ZERO foreign keys anywhere** (not even to `week_menu_plans`/`day_menus`/`meal_slots` via its `week_start_date`/`day_index`/`meal_type` columns, which superficially resemble FK'd columns elsewhere) — proven not just by schema inspection but BEHAVIORALLY: a test inserts a feedback row for a `(week_start_date, day_index, meal_type)` triple with NO corresponding `day_menus`/`meal_slots` row anywhere, and confirms the insert succeeds. This is intentional per Requirement 10.2 (feedback is an independent historical snapshot, storing its own `dish_name`/`primary_food_ids` copy) — an FK with CASCADE here would destroy feedback history every time a day/week gets regenerated, defeating Requirement 10.3's entire purpose (using recent negative feedback to influence FUTURE generation prompts). **Two judgment calls, both independently verified by review, not just accepted on the implementer's word**: (1) added `CHECK (liked IN (0,1))` even though design.md's wording for this one column is a softer parenthetical "(0 or 1)" rather than the explicit "CHECK IN (...)" phrasing used elsewhere in the same table — review cross-checked every mention of `liked`/満足度フィードバック across design.md and requirements.md and confirmed the feedback concept is consistently binary (好き/苦手) throughout with no hint of a third state anywhere, concluding the added CHECK is a safe strengthening, not a premature/risky assumption. (2) Did NOT add an explicit `CREATE INDEX` on `recipe_details.meal_slot_id` (breaking the established "always index FK columns" precedent from tasks 1.1/1.2) since it's UNIQUE on that single column alone — review independently ran a real SQLite experiment (`PRAGMA index_list`/`EXPLAIN QUERY PLAN`) and confirmed SQLite auto-creates an equivalent index for any single-column UNIQUE constraint, making an explicit index a byte-for-byte redundant duplicate; this is the FIRST single-column-UNIQUE FK in this schema, so the divergence from the blanket indexing precedent is justified by a genuinely new case, not an inconsistency. **Lesson**: when a design.md constraint's wording is less explicit/formal than its siblings in the same table (e.g. a parenthetical note vs. an explicit CHECK-IN clause), don't treat that as license to skip the constraint OR to silently add a stricter one — cross-reference the ENTIRE spec (design.md + requirements.md) for any hint the softer wording was deliberate (e.g. a hidden third state), and only add the stricter constraint once that search comes up empty.
- (1.4) `shared/src/menu.schema.ts` (new file, registered via a single added line in `shared/src/index.ts`) defines all 10 types design.md's Service Interface specifies (`MealType`, `IngredientSelection`, `NutritionValues`, `VerifiedNutritionValues`, `MealSlot`, `DayMenu`, `WeekMenuPlan`, `SupplementarySuggestion`, `RecipeDetail`, `FeedbackInput`), independently verified field-for-field against design.md with zero discrepancies. **Two consequential judgment calls, both independently traced through design.md's actual generation flow by review before approval** (not accepted on the implementer's word alone, since this is a foundational type ~35 future tasks will build on): (1) `NutritionValuesSchema` is deliberately LEFT UNCONSTRAINED (no `.nonnegative()`) since it's reused for BOTH `RecipeDetail.nutrition` (an absolute value) AND `SupplementarySuggestion.nutritionDelta` (a genuine signed delta) — directly reapplying `nutrition-engine`'s `PfcTargetsSchema` precedent (task 1.1 of that spec) for the identical "shared shape spans an absolute-value context and a delta context" reasoning. `VerifiedNutritionValuesSchema` (used for `MealSlot.nutrition`/`DayMenu.dayNutrition`, always DB-verified absolute values, never deltas) is instead built as a FULLY INDEPENDENT `z.object()` (not `.extend()`-ing the unconstrained base, which would have silently inherited its permissiveness) with all 13 fields `.nonnegative()`. (2) `DayMenu.meals`/`WeekMenuPlan.days`/`RecipeDetail.supplementarySuggestions` all enforce EXACT cardinality (`.length(4)`/`.length(7)`/`.min(1).max(2)`) at the Zod-schema level, matching design.md's "4件"/"7件"/"1〜2件" comments — review traced design.md's actual generation flow (`MenuPlanRepository.replaceWeek`/`replaceDay`) and confirmed `WeekMenuPlan`/`DayMenu` are ONLY EVER constructed as fully-assembled, post-verification, post-save objects; Claude's raw pre-verification tool output uses entirely SEPARATE types (`WeeklyGenerationToolResult`/etc., a later ClaudeMenuClient task's concern) with their own independently-enforced cardinality — so no future task can ever need to `.parse()` a partial/in-progress `WeekMenuPlan` against this fixed-length schema; the enforcement is a safe, valuable assembly-bug catcher, not a landmine. **A third, smaller judgment call**: `RecipeDetail.mealSlotId` deliberately uses PLAIN unconstrained `z.number()` (no `.int()`/`.positive()`) even though it references an AUTOINCREMENT PK — matches the actual established precedent (`daily-log.schema.ts`'s `ExerciseLogEntry.id`, also plain `z.number()`) and design.md's own `recipe_details` table, which (unlike `servings`/`cooking_time_minutes`) has no ">0" annotation on this column; review additionally confirmed `mealSlotId` never crosses the HTTP request boundary (always resolved server-side from a trusted DB row, never client-supplied), so the laxer choice carries no realistic risk. `IsoDate` (the plain type alias from `daily-log.schema.ts`) is genuinely reused, not redefined — via a local `IsoDateSchema: z.ZodType<IsoDate> = z.string()` helper, deliberately matching `daily-log.schema.ts`'s own plain (non-regex) date-string validation rather than `nutrition.schema.ts`'s stricter private (and structurally inaccessible) `IsoDateStringSchema`. The task's literal "import from server, confirm build" completion condition was satisfied via the full monorepo build succeeding (root `npm run build`, which depends on `shared` via TS project references) rather than a literal new import inside `server/src/`, since the task's own boundary explicitly forbids touching `server/src/` — this is the correct reading, not a shortcut. **Lesson**: for a foundational shared-schema task whose types will constrain many future tasks, tracing how the DOWNSTREAM consumers (later tasks' sequence diagrams / repository interfaces) will actually construct and pass around the type is the right way to validate a strictness judgment call (fixed-length arrays, numeric constraints) — don't just check whether design.md's wording technically permits the stricter reading; check whether any future task could plausibly need the LAXER reading and be blocked by it.
