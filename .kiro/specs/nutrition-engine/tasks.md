- [ ] 2.4 (P) 微量栄養素目標値ルックアップモジュール（MicronutrientCalculator）を実装する

  - 観測可能な完了条件: 年齢区分の境界値（29/30歳、64/65歳等）と性別3パターンの入力に対し、参照テーブル通りの9項目の目標値が返る。喫煙「吸う」でビタミンCが加算値分増加すること、飲酒「よく飲む」でビタミンB1が加算値分増加すること、それ以外の組み合わせ（「たまに」「しない」「null」）では加算されないことが確認できる
  - _Requirements: 6.1, 6.2, 6.3, 6.4, 6.5_
  - _Boundary: MicronutrientCalculator_

- [ ] 2.6 (P) 安全ガードレール判定モジュール（GuardrailEvaluator）を実装する

  - 減量方向（目標体重<現在体重）の場合のみ最大減量ペースを評価し、維持・増量方向ではスキップする。最低摂取カロリーは方向に関わらず常に評価する
  - 抵触時は算出済みの目標カロリー・PFCを変更せず、期間延長案・目標体重緩和案のうち少なくとも1件を含む修正提案を返す。両方に抵触した場合は両方の警告と提案を独立に返す
  - 観測可能な完了条件: 「最低カロリーのみ抵触」「最大ペースのみ抵触」「両方抵触」「いずれも抵触なし」「維持・増量方向」の5パターンそれぞれで期待通りの `GuardrailResult` が返る

  - _Requirements: 10.1, 10.2, 10.3, 11.1, 11.2, 11.3, 11.4_

## Implementation Notes
- (1.1) `shared/src/nutrition.schema.ts`'s 9 target types (`PfcRatio`, `PfcTargets`, `MicronutrientTargets`, `GuardrailSuggestion`, `GuardrailWarning`, `GuardrailResult`, `CalculationUnavailableError`, `NutritionSummary`, the date-query schema) do NOT embed any of `profile.schema.ts`'s reusable enums (`Gender`/`JobActivityLevel`/`CommuteMethod`/`RestrictionType`/`RestrictionIntensity`/`SmokingHabit`/`AlcoholHabit`) as fields — confirmed field-by-field against design.md. `GuardrailSuggestionKind`/`GuardrailWarningType` are new spec-local enums, correctly defined fresh (not duplicates). The task text's instruction to reuse profile enums applies to LATER tasks (2.1's `BmrInput`, 2.2's `ActivityCoefficientInput`, 2.4's `MicronutrientCalculator.calculateTargets` params) whose types haven't been added to `nutrition.schema.ts` yet — when those tasks add schemas for these calculator inputs, import the existing `profile.schema.ts` enum schemas rather than redefining `z.enum([...])` literals.
- (1.1) `PfcTargetsSchema`'s 6 numeric fields are deliberately left unconstrained (no `.positive()`/`.nonnegative()`), since Requirement 10.3 mandates that guardrail-violating diet-mode values be presented as-is unmodified — `DietModeCalculator`'s formula can produce a non-positive `dietMode.calorieTarget`/PFC in extreme inputs (no relative bound exists between `goalWeightKg` and current weight in `profile.schema.ts`), and a `.positive()` constraint would incorrectly reject exactly the case 10.3 protects. `MicronutrientTargetsSchema` uses `.nonnegative()` since those are static-reference-table lookups with no such edge case.
- (1.2) `server/src/nutrition/constants.ts` holds ONLY the constants this task's text names (Mifflin offsets, activity coefficient base/commute/step/MET tables + clamp bounds, the 11-row PFC ratio adjustment table, `ENERGY_DENSITY_KCAL_PER_KG`, `MIN_CALORIE_FLOOR`, `MAX_WEEKLY_LOSS_PACE_RATIO`) — deliberately does NOT include the diet-insights constants (`WEIGHT_TREND_LONG_WINDOW_DAYS`, `PLATEAU_PACE_RATIO_THRESHOLD`, `EXERCISE_SIMULATION_SCENARIO`, etc.), which belong to task 6.2. The step-adjustment table is modeled as 5 half-open `[minSteps, maxSteps)` rows (a lossless transformation of design.md's inclusive integer ranges like "5000-7499"); it has no classification function — matching a step count to a tier is deferred to task 2.2's `ActivityCoefficientCalculator`. Similarly the PFC table is a flat 11-row array (not a nested lookup) so each row could be asserted 1:1 against design.md's table; a lookup-by-(type,intensity) function is deferred to task 2.3's `PfcCalculator`. All 11 PFC rows and all 5 step-tier boundaries were independently re-transcribed from design.md and cross-checked by the reviewer with zero discrepancies — this is the highest-risk task in the spec for silent transcription errors, now verified clean.
- (2.1) Requirement 2.4 (missing height/weight/age validation) is correctly OUT of `BmrCalculator`'s scope — design.md explicitly assigns this to `NutritionService` (task 3), which is expected to pass only non-null values (enforced at the `BmrInput` TypeScript type level, `weightKg`/`heightCm`/`age` are plain `number`, not `number | null`). `BmrInput` is a local `interface` in `bmr.calculator.ts`, not a Zod schema in `shared/` — it's an internal `NutritionService`↔`BmrCalculator` contract, not an HTTP-boundary shape (this pattern likely applies to `ActivityCoefficientInput` in task 2.2 too). Design.md literally says to assert internally that BMR is positive ("算出結果が正の数値であることを内部でアサートする") — this is a real runtime `assertPositiveBmr()` check, not just documentation, because Mifflin-St Jeor is NOT unconditionally positive across the full `number > 0` domain (only for realistic human body measurements); a pathological input (e.g. very low weight/height with high age) can drive it negative. Calculator modules here are plain exported functions (not objects satisfying a named `XCalculator` interface with a `.calculate()` method as design.md's Service Interface blocks literally show) — justified since design.md's Architecture Integration states these are "純粋関数モジュール" with no injected dependencies, unlike `ProfileService`/`DailyLogService`'s factory+interface pattern. Future calculator tasks (2.2-2.6) should follow this same "plain function" convention, not the interface+factory pattern.
