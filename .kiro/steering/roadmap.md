# Roadmap

## Overview
個人利用を想定した栄養管理Webアプリケーション。ユーザーが身長・体重・年齢・性別・活動レベルなどの身体情報および生活習慣情報を入力・保存すると、必要栄養素・カロリーが自動算出され、1週間分のおすすめ献立が提示される。通常モードに加え、目標体重・達成期間を指定するダイエットモードを持ち、安全なペースでの減量を支援する。

栄養目標値は決定論的な計算式で算出し、献立内容はLLM（Claude API）が生成し、生成結果は食品成分DBと突き合わせて検証するハイブリッド構成を採る。これにより、数値の信頼性と献立の多様性・柔軟性を両立する。

## Approach Decision
- **採用**: ハイブリッド型（計算式によるBMR/TDEE/PFC/微量栄養素の算出 + Claude APIによる献立生成 + 食品成分DBによる栄養価検証）
- **理由**: LLMに栄養価計算まで任せると数値の正確性が担保できないため、数値計算は決定論的な式で担保し、LLMは献立内容（料理名・食材選定・調理手順）の生成という創造的な部分に限定して活用する。食品成分DBとの突き合わせにより、生成された献立の栄養価表示の信頼性を確保する。
- **却下した代替案**:
  - フルLLM型（栄養計算も献立生成もLLMに一任）: 実装は最も簡単だが、栄養価数値の正確性にリスクがあるため却下
  - フル定型型（固定レシピDBの組み合わせのみ、LLM不使用）: 予測可能性・コストは優れるが、献立の多様性・柔軟性という要求を満たせないため却下

## Scope
- **In**:
  - 身体情報・生活習慣情報・食事制限設定（タイプ・強度・自由記述）の入力/保存（シングルユーザー、認証機能なし）
  - 体重・体脂肪率・摂取カロリー実績・追加運動記録の日次記録（ログ）と推移グラフ
  - BMR/TDEE/PFCバランス/微量栄養素目標の計算エンジン、食事制限設定に応じたPFC比率調整
  - 消費カロリーの算出（TDEE＋追加運動ログの加算）
  - ダイエットモードの安全ガードレール（最低摂取カロリー、最大減量ペースの上限チェック）
  - Claude APIによる1週間分の献立生成（食事制限設定を反映）
  - 献立の1日単位（他日の重複回避付き）・1週間単位の再生成・差し替え
  - 食事セルのオンデマンドなレシピ詳細生成・追加副菜提案
  - 献立への満足度フィードバック（好き/苦手）収集と次回生成への反映
  - 食品成分DB（MEXT 日本食品標準成分表 八訂）との栄養価突き合わせ検証
  - 通常結果・ダイエット結果の表示（栄養充足率の可視化、買い物リスト、レシピ詳細、摂取/消費カロリー収支、体重推移・目標達成予測グラフ等）
  - レスポンシブ対応のWebアプリケーション（ブラウザ利用）
- **Out**（将来拡張候補）:
  - マルチユーザー・認証機能
  - リマインド通知機能
  - 血液検査データ等の外部連携
  - 献立の栄養計算までLLMに一任する方式

## Constraints
- LLMはClaude API（Anthropic Messages API）を使用する
- 食品成分DBはMEXT「日本食品標準成分表（八訂）増補2023」を一次データソースとし、利用時は出典表示（"日本食品標準成分表（八訂）増補2023年から引用"）を行う。私的出版社（医歯薬出版）の独自デジタル版はEULAが制限的なため使用しない
- 献立生成時、Claudeには食材を自由記述させず、既知の食品ID一覧からのtool呼び出し（`strict: true` の構造化出力）で選択させ、DB照合を決定論的にする
- 分量単位（g / 個 / 大さじ 等）の正規化テーブルを別途用意する
- 技術スタック（言語・フレームワーク・DB）は未定。design フェーズ（`/kiro-spec-design`）で提案する
- シングルユーザー想定のため、認証・認可の実装は不要

## Boundary Strategy
- **なぜこの分割か**: 「入力/保存とログ」「数値計算」「LLMによる献立生成」「結果表示」は責務が明確に異なり、それぞれ独立してテスト・改修可能な単位になる。特にLLM連携部分（menu-generation）は他と切り離すことで、プロンプト調整やコスト管理の変更が計算ロジックに影響しないようにできる。
- **注意が必要な共有境界**:
  - `user-profile` が保存するデータ形式（身体情報・嗜好・NG食材等）は `nutrition-engine` と `menu-generation` の両方が参照するため、スキーマ変更時は両specに影響する
  - `nutrition-engine` が算出する目標値（カロリー・PFC・微量栄養素）のフォーマットは `menu-generation` の入力および `results-dashboard` の表示の両方に使われるため、インターフェースの一貫性に注意する
  - ダイエットモードの安全ガードレール判定結果（警告・修正提案）は `nutrition-engine` で算出し、`results-dashboard` で表示するため、両spec間でメッセージ形式の合意が必要
  - 摂取カロリーは `menu-generation` の計画kcalを `user-profile` の日次ログがデフォルト値として取り込み、`nutrition-engine` の消費カロリーと突き合わせて `results-dashboard` が表示する三者間の連携になるため、データの受け渡し形式に注意する

## Specs (dependency order)
- [x] user-profile -- 身体情報・運動習慣（お仕事中の活動度・通勤手段・場面別の週間運動量）・食事制限設定の入力/保存、体重体脂肪率・摂取カロリー実績・運動記録の日次ログと推移グラフ。Dependencies: none
- [x] nutrition-engine -- 運動習慣データからの活動レベル算出、BMR/TDEE/PFC/微量栄養素の計算エンジン、食事制限設定に応じたPFC比率調整、消費カロリー算出とダイエットモード安全ガードレール。amendment: 体重推移予測・目標達成見込み・停滞期検知・運動併用シミュレーション（`GET /api/nutrition/diet-insights`）を追加。Dependencies: user-profile
- [x] menu-generation -- Claude APIによる1週間献立生成（食事制限設定反映）、食品成分DB照合検証、1日単位/1週間単位の差し替え、食事セルのレシピ詳細・追加副菜提案、満足度フィードバック学習。amendment: 週間買い物リスト生成（自然単位表示対応）・外食代替提案を追加。Dependencies: user-profile, nutrition-engine
- [x] results-dashboard -- 通常結果/ダイエット結果画面、栄養充足率可視化、買い物リスト、レシピ詳細モーダル、摂取/消費カロリー収支、体重推移・目標達成予測グラフ。独自の計算ロジックは持たず、各specの公開APIをフロントエンドから直接呼び出す構成に確定。Dependencies: nutrition-engine, menu-generation

すべてのspecでrequirements/design/tasksが確定し、クロススペックレビュー完了（`activityLevelLabel`のタスク欠落、`EatingOutSuggestionResult`の型定義欠落、results-dashboardの解消済みフラグの更新漏れ、mockup.htmlの微量栄養素表示とnutrition-engineの実際の算出項目の不一致、を修正済み）。次のステップは `/kiro-impl <feature>` での実装。
